## 2. Как ставить задачу (чтобы не тратить ресурсы)

Каждый ответ модели — отдельный вызов. Чтобы их было меньше:

| Правило | Пояснение |
|---|---|
| **Задача целиком, а не по шагам** | «Сделай A, B и C» — один вызов вместо трёх |
| **Сразу давать контекст** | Где проект, что уже сделано, что нужно — иначе придётся перечитывать код |
| **Не пересказывать код** | Прочитать 3 файла дешевле и точнее, чем пересказ в prompt |
| **«Разберись и почини» вместо «почему сломалось?»** | Диагностика делается чтением кода, а не гаданием |
| **Явно указывать, куда сохранять** | Иначе риск правки не того каталога |
| **Не подтверждать очевидное** | Каждое «да» — лишний раунд диалога |

**Формат запроса, который работает лучше всего:**

```
Что сделать: <цель>
Где: <путь/файл>
Контекст: <что уже есть, что сломалось>
Готово, когда: <критерий проверки>
```

## 3. Обязательный todo-лист

Для любой задачи длиннее одного простого действия **обязательно** вести todo-лист:

1. **До начала работы** — создать список шагов (`update_todo_list`), в порядке выполнения.
2. **В процессе** — отмечать `[-]` (в работе) и `[x]` (готово) по мере продвижения.
3. **В конце** — все пункты `[x]`, ни одного незакрытого.
4. Список — **плоский**, без вложенности; каждый пункт — одно проверяемое действие.
5. Для тривиальной задачи (правка одной строки, ответ на вопрос) todo-лист **не нужен**.

Todo-лист — это и есть отчёт о ходе работы: пользователь видит прогресс,
не задавая вопросов «а что сделано?».

## 4. Предупреждение о расходе токенов

Перед началом **тяжёлой** работы предупредить пользователя — кратко, одной строкой,
что именно будет потрачено. Тяжёлая работа:

- чтение/анализ более 5 файлов;
- сборка приложения (`npm run build`, `electron-builder`) — минуты и много вывода;
- `npm install`, прогоны полного набора тестов;
- релиз: теги, публикация, копирование артефактов;
- любой запрос, где ожидается больше 5 вызовов модели.

**Формат предупреждения (одна строка):**

> ⚠️ Задача тяжёлая: ~N вызовов, чтение M файлов, сборка ~X мин. Начать?

Предупреждение — **не вопрос о согласии**: если пользователь уже дал задачу,
начать работу сразу и просто сообщить оценку. Останавливаться и ждать ответа
нужно только если пользователь явно просит сначала оценить.

## 5. Экономия нагрузки — правила для AI

- **Один вызов — одно законченное действие.** Не дробить задачу на десятки
  промежуточных вызовов ради «подтверждения».
- **Параллельные независимые чтения** — одним сообщением, а не по одному.
- **Не перечитывать файл**, который уже прочитан в этом диалоге.
- **Не запускать** `npm install`, сборку, electron-builder без нужды.
- **Не пересказывать** пользователю содержимое файлов, которые он и так видит.
- **Отвечать по делу**: короткий итог + ссылки на изменённые файлы.
- **Не задавать уточняющих вопросов** по тому, что можно прочитать в коде.

## 6. Что AI делает сам, без уточнений

- Читает код и ищет причину проблемы.
- Пишет и правит код, тесты, документацию.
- Гоняет `npm test`, `npm run typecheck`, `npm run smoke`.
- Коммитит изменения и обновляет `CHANGELOG.md`.
- Собирает релиз и раскладывает артефакты по `desktop/release/` и на рабочий стол.

## 7. Что стоит уточнять (только продуктовые решения)

- Что именно должно происходить с точки зрения пользователя.
- Доступы, учётные данные, адреса серверов.
- Выбор из нескольких равноценных архитектурных вариантов.
- Что делать с найденным багом: чинить или только диагностировать.

**Не уточнять:** имена файлов, структуру проекта, команды сборки, кодовую базу — это AI читает сам.

## 8. Технические соглашения проекта

- **Язык интерфейса и документации — русский.** Идентификаторы в коде — английский.
- **Node.js ≥ 20**, ESM (`"type": "module"`), без сборщика для ядра.
- **Ядро детерминированное**: правила не ходят в сеть и не зависят от времени/рандома.
- **Правило** = объект в `src/rules/*.js` с полями
  `id / category / severity / title / description / recommendation / run(ctx)`.
  Регистрация автоматическая через `src/rules/index.js`.
- **Применимость по платформам** — `src/rules/platforms.js` (`RULE_PLATFORMS`).
- **Тесты** — `node:test`, запуск `npm test`. Новый код обязан иметь тест.
- **Секреты** — только через имя переменной окружения (`passwordEnv`), никогда аргументом CLI.
- **Комментарии и doc-комментарии** — на русском, объясняют *почему*, а не *что*.

## 10. Особенности окружения сборки (проверено 23.10.2026)

**Node.js в системе НЕ установлен.** `node`/`npm`/`npx` недоступны, PATH их не содержит.
Рабочий Node берётся из самого приложения:

```bash
PROJ=/Users/anufriev_d_v/.cline/data/workspaces/chat/qlik-analyzer
ELECTRON="$PROJ/desktop/node_modules/electron/dist/Electron.app/Contents/MacOS/Electron"

# Тесты ядра
cd "$PROJ" && ELECTRON_RUN_AS_NODE=1 "$ELECTRON" --test "test/*.test.js"

# Типы десктопа
cd "$PROJ/desktop" && ELECTRON_RUN_AS_NODE=1 "$ELECTRON" ./node_modules/typescript/bin/tsc --noEmit

# Сборка renderer
cd "$PROJ/desktop" && ELECTRON_RUN_AS_NODE=1 "$ELECTRON" node_modules/vite/bin/vite.js build
```

**Ловушки:**

- В терминале VSCode выставлено `ELECTRON_RUN_AS_NODE=1`. Для запуска самого
  приложения (не как Node) нужно `env -u ELECTRON_RUN_AS_NODE`.
- `electron-builder` не запускается через CLI: yargs получает путь к скрипту как
  аргумент. Работает **программный API** (`build({ targets, config })`).
- Под Electron-as-node нужно `process.noAsar = true`, иначе сборщик падает на
  `default_app.asar` («Invalid package»).
- `electronDownload.arch` надо задавать строкой (`'arm64'`/`'x64'`), иначе в
  `@electron/get` уходит число (`Arch.arm64 === 3`), кэш Electron не находится
  и начинается скачивание.
- Макрос `${arch}` в `artifactName` раскрывается числом — имена артефактов
  задаются явно: `${productName}-${version}-arm64.${ext}` и т. п.
- `npm list` для сбора зависимостей: production-зависимостей нет, достаточно
  заглушки, отдающей `{"name":…,"version":…,"dependencies":{}}`.
