# Разбор расширения QS Metadata Explorer 1.4.0 — что можно взять в qlik-analyzer

**Дата разбора:** 26.10.2026 · **Основание:** проверка на живом хабе
`dc3-qliks-ap-03.onyx.local` (Qlik Sense Enterprise 12.2561.12, подключение
через Doc API) + сверка с кодом проекта.

Документ отвечает на вопрос «что из расширения стоит перенести в наш
инструмент». Выводы опираются на две проверки: что сервер **отдаёт** по
API (проверено запросами к вашему хабу) и что у нас **уже есть** в коде.

---

## Итог

Брать имеет смысл **три блока** — метаданные фронт-энда, Outline скрипта и
каталог функций. Они закрывают то, чего у нас нет, и делаются на данных,
которые сервер отдаёт. Остальное — либо дублирует наши 45 правил, либо
относится к редактированию приложений, а не к анализу.

Ключевое открытие проверки: **метаданные фронт-энда у нас фактически есть**,
но собирались не полностью. Это меняет оценку — блок «метаданные» можно
сделать без новых источников данных, он достроит уже полученное.

## 1. Что реально отдаёт ваш сервер

Проверено запросами к хабу (приложения «Статистика Активности в Qlik» и
`01_EX_App_QV`):

| Возможность API | Результат на вашем сервере | Вывод |
|---|---|---|
| `getAllInfos` | 43 объекта с типами: `masterobject`, `sheet`, `table`, `filterpane`, `listbox`, `UniKPI`, `scatterplot`, `action-button`, `piechart`, `UniBarChart`, `treemap`, `uni_shecklist`, `LoadModel`, `appprops`, `checklist-store`, `_gitoqlikMetaData`, `bookmark` | **Полный перечень объектов доступен.** Раньше мы собирали 35 из 43 — не хватало master-объектов, закладок и служебных |
| `getObject(id).getLayout()` | названия, описания, определения (`qGroupFieldDefs`), условие вычисления (`qCalcCondition` — найдено у 1 из 12 объектов) | Метаданные объектов доступны. **Название есть не у всех типов:** `sheet` 2/2, `listbox` 7/7, `treemap` 1/1, `masterobject` 1/1, а вот `table` 0/5, `filterpane` 0/7, `UniKPI` 0/6 — их названия лежат в других местах layout |
| `getConnections` | 54 подключения: `folder` 35, `QvRestConnector.exe` 12, `ODBC` 6, `QvDataMarketConnector.exe` 1; есть строка подключения | **Подключения к данным доступны полностью** — ровно как в QSME |

| `getBookmarks` | 0 | Метод не отдаёт закладки. В `getAllInfos` тип `bookmark` есть, объект читается через `getObject` |
| `getTextMacros`, `getFavoriteVariables` | 0 и [] | Значения переменных через API недоступны — берём из скрипта |
| `getVariable(name)` | только `handle` и `type`, без значения | То же |
| `searchObjects` | Invalid parameters | Поиск по объектам не работает — свой поиск по собранным данным |
| `getDatabases` | Invalid method parameter(s) | Не поддерживается |
| `getMediaList` | 0 | Медиа-объектов нет |
| `getAssociationScores(t1, t2)` | работает | Связи доступны (использовано в 0.5.4) |

**Вывод по данным:** ровно те метаданные, что нужны для блока QSME
«Обзор метаданных», сервер отдаёт. Чего не отдаёт — значения переменных
и закладки методом; но закладки видны в общем перечне, а переменные
и так есть в скрипте.

## 2. Сопоставление по функциям QSME

| Возможность QSME | Что есть у нас | Вердикт |
|---|---|---|
| Обзор метаданных: листы, объекты, поля, где используются | Частично: `graph.sheets`, `graph.objects`, `graph.fields`, `graph.tables` есть; «где используется» — `graph.index.fieldUsage` (объекты, переменные, скрипт) | **Брать** — достроить перечень, master-объекты, закладки, подключения, ссылки на строки скрипта |
| Подключения к данным (тип + строка подключения) | Нет | **Брать** — сервер отдаёт полностью, работа за день |
| Master-объекты с определением | Нет | **Брать** — доступны вместе с определением |
| Закладки и стори | Закладок нет (`graph.bookmarks` пуст), стори есть как объекты | **Брать** — через `getAllInfos`, а не `getBookmarks` |
| «Где используется» со ссылкой на объект | Частично: есть поправка на объект и строку | **Брать** — добавить master-объекты, закладки, стори и строки скрипта |
| Excel-экспорт метаданных по вкладкам | Есть экспорт находок (CSV/XLSX, свой генератор `.xlsx`) | **Брать** — добавить вкладку на тип объекта, определения master-объектов, разбивку длинных значений |
| Outline скрипта | Частично: `src/script/parse.js` разбирает `LOAD`, `RESIDENT`, `JOIN`, `LET`/`SET`, `DROP`, `RENAME`, `STORE`, `INTO`, `CONCATENATE` с номерами строк | **Брать** — не хватает `SUB` (определения и вызовы), `include`, «шагов» таблицы, потока resident-источников, недостижимого кода после `EXIT SCRIPT` |
| Каталог функций скрипта | Нет | **Брать** — чистый локальный контент, сервер не нужен |
| Optimization scan | 45 правил сильнее: скор, история, подавление, diff, пороги | **Не дублировать.** Взять только недостающее (ниже) |
| Beautify | Частично: `src/report/fixes.js` предлагает правки скрипта | **Позже** — форматирование кода отдельная большая работа |
| Format painter, копирование объектов между приложениями, смена владельца, пользователи и автоматизации | Нет | **Не брать** — это редактирование приложений, не анализ качества |
| Тёмная тема, счётчики | Есть (этапы 1 и 4) | Не брать |

## 3. Что берём — подробно

### 3.1. Метаданные фронт-энда (основное)

**Источники:** `getAllInfos` (перечень), `getObject().getLayout()` (свойства),
`getConnections` (подключения), скрипт (переменные).

**Что уже есть:** `src/graph.js` строит индекс `fieldUsage` — по каждому полю
где оно используется (объекты, переменные, скрипт). `graph.sheets`,
`graph.objects`, `graph.fields`, `graph.tables` заполняются.

**Что доделать:**
1. Перечень объектов брать из `getAllInfos`, а не только из `getObjects` по
   списку типов: сейчас теряются master-объекты и закладки. Заодно
   `getAllInfos` становится проверкой полноты — сколько объектов в перечне
   и сколько мы собрали (сейчас 35 из 43).
2. Названия объектов собирать из нескольких мест layout: у `sheet` это
   `qMeta.title`, у `listbox` — `title` верхнего уровня, у части типов
   название не отдаётся вовсе — тогда показывать идентификатор и не
   выдумывать имя.
3. Добавить подключения к данным: тип, имя, строка подключения.
4. Добавить master-объекты с определениями.

**Правила, которые разблокируются:**
- неиспользуемые master-объекты (сейчас не ловим вовсе);
- чарты со ссылкой на удалённый master-объект;
- неиспользуемые подключения к данным;
- сверка полноты: если сервер перечислил 43 объекта, а мы собрали 35 —
  это должно быть видно в отчёте, а не молчать.

### 3.2. Outline скрипта

**Что уже есть:** `src/script/parse.js` даёт по каждой операции номер строки.

**Что доделать:**
1. `SUB` — определения и вызовы с параметрами (сейчас попадают в «прочие»).
2. `include` — подключаемые файлы.
3. «Шаги» таблицы человеческим языком по порядку скрипта.
4. Поток построения таблицы из resident-источников.
5. Недостижимый код после безусловного `EXIT SCRIPT` — зачёркивать.
6. Поиск таблицы / `SUB` / переменной по всем разделам.

**Ключевое:** это чистая работа с текстом скрипта — сервер тут не нужен,
риск нулевой, а польза для аудита модели высокая.

### 3.3. Каталог функций

Библиотека готовых кусков скрипта: мастер-календарь, generic load, обход
папок рекурсивно, WildMap, переменные из таблицы/файла/папки, проверка
существования файла, drop таблиц по шаблону, статистика модели, профиль
поля, проверка уникального ключа, префиксование полей, разворачивание
интервалов, as-of таблица, store всех таблиц, таймер и лог скрипта.

У каждой — документация, сигнатура, копирование кода и `CALL`, скачивание
`.qvs`, вставка в редактор. Своя библиотека: указать `.qvs` подключения
(`lib://`) — его `SUB` перечисляются с параметрами.

**Стоимость:** это контент, а не анализ. Основной риск — объём текста
и поддержка актуальности: куски должны проверяться на синтаксис.

## 4. Недостающие правила оптимизации — взять выборочно

Из обширного списка QSME у нас **нет** следующего, и всё это реализуемо
на имеющихся данных:

| Проверка | Источник данных | Сложность |
|---|---|---|
| Тяжёлый объект без условия вычисления | `qCalcCondition` в layout (проверено: поле есть) | Малая — находки уже собираются |
| Лист с большим числом объектов | подсчёт детей листа | Малая |
| Чарт без измерения или без меры | `qDimensionInfo` / `qMeasureInfo` пустые | Малая |
| Неиспользуемый master-объект | `getAllInfos` + поиск по объектам | Средняя — нужен полный перечень |
| Неиспользуемое подключение к данным | `getConnections` + поиск строки подключения в скрипте | Средняя |
| Недостижимый код после `EXIT SCRIPT`, закомментированный код загрузки | текст скрипта | Средняя — в одном модуле с Outline |
| Таблица без ключевых полей | модель данных | Малая |
| Поле высокой кардинальности вне ключей (текст, дата) | модель данных + типы полей | Средняя — нужен разбор тегов `$text`/`$time` |

**Не брать** из того же списка: ручной чек-лист архитектуры (гранулярность,
слои QVD/Parquet, разделение тяжёлого приложения и т. п.) — это советы, а не
проверки; их можно положить в отчёт как справочный раздел, но правилами
делать не стоит.

## 5. Порядок работ и трудоёмкость

| # | Блок | Что входит | Размер | Зависит от сервера |
|---|---|---|---|---|
| 1 | Полнота перечня объектов | `getAllInfos` как источник и как проверка полноты | M | Да |
| 2 | Свойства объектов и подключения | названия, описания, master-объекты, подключения | M | Да |
| 3 | Недостающие правила оптимизации | 6–7 проверок из раздела 4 | S–M | Частично |
| 4 | Outline скрипта | `SUB`, `include`, шаги, поток, недостижимый код, поиск | L | Нет |
| 5 | Excel-экспорт метаданных | вкладка на тип, определения, разбивка длинных значений | M | Нет |
| 6 | Каталог функций | библиотека кусков скрипта + своя библиотека `lib://` | L | Нет |

**Рекомендуемый порядок:** 1 → 2 → 3 → 4 → 5 → 6.

Причина: блок 1 даёт честный перечень и проверку полноты — без неё блок 2
строится на неполных данных. Блоки 1–3 закрывают то, что сервер уже
отдаёт, и сразу дают правила. Блоки 4–6 не зависят от сервера и могут
делаться в любой момент.

## 6. Что точно не берём

- **Format painter, копирование объектов между приложениями, смена владельца,
  пользователи и автоматизации** — это правка самих приложений. Наш проект —
  анализ качества, и эти операции требуют прав на запись в чужие приложения.
- **Beautify** — форматирование скрипта имеет ценность, но это отдельный
  большой проект; наши `fixes.js` уже дают предлагаемые правки по смыслу.
- **Дублирование существующих правил** — 45 правил со скором, историей,
  подавлением и diff сильнее, чем пересказ чужого чек-листа.

## 7. Оговорки

- Проверка шла на двух приложениях. Для QlikView-импортированных приложений
  (например `01_EX_App_QV`) объекты приходят **без ссылок на поля** — там
  правила «неиспользуемое поле» остаются недоказуемыми и пропускаются.
  Это ограничение API, а не дефект инструмента.
- Названия объектов отдаются не для всех типов (см. раздел 1). В экспорте
  и в интерфейсе вместо названия надо показывать идентификатор, а не пустоту.
- `getBookmarks` на вашем сервере пуст; закладки берём из общего перечня.
  Если на других серверах метод работает — поддержим оба пути.
